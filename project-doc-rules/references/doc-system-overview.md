# 阶段 0：体系总览与档位判断

> 读完后确定 `{tier}`，向用户简述蓝图，然后进入阶段 1。本阶段不写任何文件。

## 一、三层体系是什么

| 层 | 载体 | 回答的问题 | 关键纪律 |
|---|---|---|---|
| **规则层** | `AGENTS.md`（项目根，<150 行） | 「代码放哪里、怎么写、按什么流程」——Agent 行为约束 | 单一入口；**不重复规格内容**，只引用；规则只增补不展开 |
| **规格层** | `*_PLAN.md` / `*_SPEC.md` | 「做什么、为什么、验收标准」——每个功能线一份开工依据 | 头部元数据三件套（状态行/台账引用/既定约束）；冲突时**规格 > 规则**，先改规格再改代码 |
| **决议层** | `ledger/`（LEDGER_RULES + INDEX + 每版本一份账本） | 「每个决定是什么时候、依据什么做的」——一条决议一条记录 | 全局编号 `dN` 追加-only、跨版本不重置；状态机（进行中=唯一可写）；脚本机器校验 |

## 二、为什么是这三层（实测收益）

1. **渐进引用控上下文**：Agent 从最小的 AGENTS.md 进入，按需下钻到规格/台账，永远不必一次加载全套文档。
2. **切文件防膨胀**：台账一版本一文件 + INDEX 一行一版本；规格定稿后可整体替换为新版 v2，历史决议由台账兜底。数百条决议后单文件仍可控。
3. **机器可校验**：编号连续性、索引一致性交给脚本（退出码判损坏），不靠人眼——这是编号体系能长期存活的唯一保障。
4. **决议可追溯**：`依据：文档§章节 或 上游 dN` 字段让任何决定能沿链回溯，Agent 换会话后不丢上下文。

## 三、档位判断（访谈树根决策轮）

档位是访谈树的根决策：**先自查下表四项给出推荐（每项注明观察依据），再按 interview-guide.md 的根决策轮格式编号发给用户**——两票以上多数即推荐档位，用户答「是」即接受；拿不准时不要自行升级档位（过度建设的台账对个人小仓库是纯负担）。

| 判断项 | 倾向 full | 倾向 lean | 倾向 minimal |
|---|---|---|---|
| 项目性质 | 正式产品/多人协作 | 个人长期项目 | 小工具、脚本、一次性 |
| 功能线 | 多条并行、各有方案期 | 少量功能线 | 单一功能 |
| 开发方式 | AI Agent 长期主导，需跨会话追溯 | Agent 参与，决议量中等 | 偶尔改改 |
| 需要追溯决议 | 是（审计/回滚/归档） | 是，但量不大 | 否 |

各档产出：

- **full**：AGENTS.md + `docs/SPEC_TEMPLATE.md` 规格模板 + ledger/ 三件套 + 校验脚本。
- **lean**：AGENTS.md + ledger/ 三件套 + 校验脚本（规格条款以一段「文档与命名」写进 AGENTS.md，阶段 2 只做这一步）。
- **minimal**：仅 AGENTS.md（阶段 2–4 跳过，但 AGENTS.md 中仍写入命名规范与「规格先行」原则的简版）。

## 四、开工前需要采集的信息（事实自查清单，进入阶段 1 前完成）

按 interview-guide.md 事实/决策二分执行——下列各项**先自查，查得到的不问用户**；查不到才升级为对用户的决策提问：

- 项目名 `{project_name}`、当前版本号 `{version}`：读 git tag / 包管理清单。
- 项目一句话定位（技术栈、平台）：读 README / 构建脚本，作为根决策轮的推荐依据。
- 既有文档盘点：已有哪些 md？是否有类 AGENTS 规则文件？是否已有决策记录习惯？
  —— 既有文件**迁移而非推翻**：能映射进三层结构的就归位，冲突处向用户确认取舍（这是决策，必问）。

自查完毕 → 根决策轮确认档位 → 进入阶段 1（`interview-guide.md` + `agents-md-guide.md`）。
